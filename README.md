# CashGuard — выявление нарушений кассовой дисциплины по видео

**ForteBank Datathon 26.** Сервис принимает видеозапись с камеры кассового узла, находит эпизоды, похожие на нарушения кассовой дисциплины, и для каждого показывает тип, таймкод, кадры-доказательства, описание увиденного и пункт нормативного акта НБРК.

Результат — подсказка для проверяющего, а не юридическое или дисциплинарное заключение. Сервис оценивает только то, что видно на видео.

## Как это работает

```
 видео .mov
    │
    ▼
 кадры 2 FPS (OpenCV)
    │
    ▼
 скользящие окна: 4 с (8 кадров), шаг 2 с — всё видео без пропусков
    │
    ▼
 Qwen2.5-VL-7B-Instruct + LoRA (vLLM, локально) — каждое окно, параллельно
    │   ответ: {"violations": [{"type", "description"}]}
    ▼
 привязка типа к правилу из rules_kb.json (неизвестные типы отбрасываются)
    │
    ▼
 склейка одного нарушения из соседних окон → таймкод = середина серии окон
    │
    ▼
 3 кадра-доказательства из оригинального видео (t−0.5, t, t+0.5)
    │
    ▼
 вердикт: violation / no_violation
```

Компоненты:

| Компонент | Технология | Порт |
|---|---|---|
| VLM-сервер | vLLM, Qwen2.5-VL-7B-Instruct + LoRA (вмёржена), bf16 | 8000 (только внутри) |
| Бэкенд | FastAPI, OpenCV, очередь задач | 8080 |
| Интерфейс | Next.js | 3000 |

Все модели работают внутри сервиса. Видео, кадры и описания не передаются во внешние AI-сервисы. После загрузки весов интернет не нужен, поэтому сервис переносится во внутренний контур банка как есть (`docker-compose.yml`).

### Почему таймкод — центр окна

В обучающем датасете клип для нарушения — 4 секунды вокруг размеченного момента, то есть нарушение всегда в центре клипа. Поэтому модель отвечает на вопрос «есть ли нарушение в этом окне», а время считает бэкенд: середина серии соседних окон, где модель увидела одно и то же нарушение. Точность — около ±1–2 с при шаге окон 2 с.

### Почему нет фильтра «статичных» сцен

Деньги без присмотра, открытый сейф и незакрытая дверь — статичные сцены. Фильтр по движению выбрасывал бы именно их, а пропуск нарушения для банка недопустим. Поэтому анализируется всё видео: на RTX 4090 ролик 145 с — это около 72 окон и 1–2 минуты.

## Модель

**Qwen2.5-VL-7B-Instruct** (Alibaba, Apache 2.0 — коммерческое использование разрешено), дообучена QLoRA на датасете хакатона.

| Параметр | Значение |
|---|---|
| Метод | QLoRA 4-bit (bitsandbytes), LLaMA-Factory |
| LoRA | r = 16, α = 32, dropout 0.05, все линейные слои языковой модели |
| Визуальный энкодер | заморожен |
| Данные | 42 размеченных видео → 304 клипа train / 53 val (позитивы ± аугментации, негативы из чистых участков) |
| Обучение | 3 эпохи, lr 1e-4 cosine, эффективный batch 8, fp16 |
| Вход | 8 кадров 512 px + короткая инструкция на русском |
| Выход | JSON `{"violations": [{"type", "timecode_sec", "description"}]}` |

Код подготовки датасета: `ml/prepare_dataset.py`. Ноутбук обучения: `ml/CashGuard_Qwen2_5_VL_LoRA_Colab.ipynb`. Мёрж адаптера: `ml/merge_lora.yaml`.

Если адаптера нет, сервис работает на базовой модели в режиме `PROMPT_MODE=rules`: в промпт подаются все правила из базы знаний, а на кадры наносится таймкод.

## Нормативные источники

Только открытые акты РК.

| Документ | Что используется |
|---|---|
| [Постановление Правления НБРК от 29.11.2019 № 231](https://adilet.zan.kz/rus/docs/V1900019680) «Об утверждении Правил осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей в банках второго уровня…» (рег. № 19680) | п. 12 — личные вещи вне кассового узла; п. 19 — приём наличных: установление личности, пересчёт, проверка; п. 20 — приём и пересчёт в присутствии клиента, хранение на рабочем месте в запираемых ёмкостях; п. 21 — приём отдельно по каждому документу; п. 22 — кассир не покидает рабочее место до завершения операции; п. 31 — пересчёт суммы в присутствии клиента перед выдачей |
| [Постановление Правления НБРК от 24.02.2020 № 14](https://adilet.zan.kz/rus/docs/V2000020075) «Об утверждении Правил организации охраны и устройства помещений банков второго уровня…» (рег. № 20075) | п. 8 — кассовый узел отделён от других помещений запираемым входом |

**Как правило связано с видео.** Для каждого правила в `backend/rules_kb.json` записаны визуальные признаки, условие фиксации и источник (документ + пункт). Модель возвращает только тип и описание увиденного. Название типа и ссылку на норму бэкенд подставляет из базы знаний — модель не может выдумать пункт. Тип, которого нет в базе, отбрасывается.

## Распознаваемые нарушения

| Код | Нарушение | Что должно быть видно | Источник |
|---|---|---|---|
| `NO_CLIENT_ID_CHECK` | Приём наличных без идентификации клиента | Кассир принимает деньги без предъявления и проверки документа | № 231, п. 19 |
| `NO_RECOUNT_OR_AUTH_CHECK` | Нет пересчёта или проверки подлинности | Деньги убираются без ручного или машинного пересчёта | № 231, п. 19, 20 |
| `INCOMPLETE_CASH_PAYOUT` | Неполная выдача наличных | Клиенту передаётся только часть отсчитанной суммы | № 231, п. 31 |
| `CASH_OR_BAG_LEFT_UNATTENDED` | Деньги или инкассаторская сумка без присмотра | Наличные на открытом столе вне ёмкости, кассир отвлечён или отсутствует | № 231, п. 20 |
| `SIMULTANEOUS_CLIENTS_OR_CASH_MIXING` | Два клиента одновременно, смешивание денег | Приём у второго клиента до завершения операции с первым | № 231, п. 20, 21 |
| `CASHIER_LEFT_WORKPLACE` | Кассир покинул рабочее место | Уход из кабины до завершения обслуживания | № 231, п. 22 |
| `SAFE_LEFT_OPEN_OR_KEY_IN_LOCK` | Открытый сейф или ключ в замке | Дверца открыта после операции / ключ в скважине без присмотра | № 231, п. 20 |
| `CASH_DOOR_LEFT_OPEN` | Незакрытая дверь кассового узла | Дверь остаётся открытой, в служебную зону может пройти посторонний | № 14, п. 8 |
| `PERSONAL_ITEMS_ON_DESK` | Личные вещи на кассовом столе | Сумка или бытовые предметы кассира на рабочем столе | № 231, п. 12 |
| `CLIENT_LEFT_DURING_RECOUNT` | Клиент ушёл до конца пересчёта | Клиент покидает кассу, пока его деньги пересчитываются | № 231, п. 20 |

## Ограничения и известные ошибки

- **Мало данных.** 42 видео, по 2–9 примеров на тип. Редкие типы (неполная выдача, личные вещи) распознаются хуже частых.
- **Валидация оптимистична.** Аугментированные копии одного клипа могли попасть и в train, и в val, поэтому метрики на val завышены.
- **Таймкод ±1–2 с.** Это центр окна, а не точный кадр события.
- **Нарушения «по бездействию»** (не проверил документ, не пересчитал) требуют видеть всю операцию. Если операция длиннее окна 4 с, модель может её пропустить или отметить ложно.
- **Другой ракурс.** Обучение — на одной камере сверху. Аугментации (перспектива, поворот, яркость) частично это компенсируют, но точность на другом угле ниже.
- **Сервис не делает выводов о невидимом**: корректность проводки, суммы в системе, подлинность купюр на глаз.
- **Лица не распознаются и не идентифицируются.**
- **Один GPU.** Видео обрабатываются по очереди; внутри видео окна идут в vLLM параллельно. Бюджет на видео — 240 с; если не уложились, результат строится по проверенным окнам, а UI показывает, сколько фрагментов не проверено.
- Если VLM недоступна, задача завершается со статусом `failed` — сервис не выдаёт пустой или выдуманный результат.

## Запуск

### На GPU-поде RunPod (как развёрнуто для жюри)

Под: RTX 4090 / A5000 / L40S (24+ ГБ VRAM), шаблон PyTorch, открыть HTTP-порты **3000** и **8080**, диск 60+ ГБ.

```bash
git clone https://github.com/xJam-byte/Datathon_analysis_of_comp_vision.git /workspace/datathon
cd /workspace/datathon
export API_KEY="<свой-ключ>"

bash deploy/runpod.sh setup        # vLLM, зависимости, сборка интерфейса (~10 мин)

# дообученная модель: распаковать адаптер из Colab в ml/lora/ и вмёржить
unzip cashguard_lora_final.zip -d ml/lora
bash deploy/runpod.sh merge        # → ml/merged_model (~10 мин)

bash deploy/runpod.sh start        # vLLM + бэкенд + интерфейс
```

Без адаптера `start` поднимет базовую модель в режиме `rules`. Логи — в `deploy/logs/`.

### Docker Compose (перенос во внутренний контур)

Нужны Docker, NVIDIA Container Toolkit и GPU 24+ ГБ.

```bash
export API_KEY="<свой-ключ>"
export MODEL_PATH=/app/ml/merged_model     # или Qwen/Qwen2.5-VL-7B-Instruct + PROMPT_MODE=rules
docker compose up --build -d
```

### Переменные бэкенда

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `API_KEY` | — | ключ для `X-API-Key` (задать обязательно) |
| `VLM_BASE_URL` | `http://localhost:8000/v1` | адрес vLLM |
| `PROMPT_MODE` | `finetuned` | `finetuned` — дообученная модель, `rules` — базовая |
| `WINDOW_SIZE_SEC` / `WINDOW_STRIDE_SEC` | 4 / 2 | окно и шаг |
| `VLM_CONCURRENCY` | 6 | параллельных запросов к vLLM |
| `PROCESSING_BUDGET_SEC` | 240 | бюджет времени на одно видео |
| `MOTION_FILTER` | `false` | отсечение статичных окон (не рекомендуется) |
